# 火币合约行情分析 · 投资建议 (investment-advisory-bot)

拉取火币（HTX）USDT 本位永续合约行情，做多因子打分，输出**可执行**的交易计划：
方向、入场区间、止损、止盈目标、盈亏比，以及按账户权益反推的**张数 / 保证金 / 止损亏损**。

带一个网页控制台：可以选币种、看 K 线与关键价位、也可以开**定时任务循环执行**并把信号落库。

> 只读行情、不下单。所有内容都是分析结果，不构成投资建议。

---

## 快速开始

```bat
run.bat
```

浏览器会自动打开 <http://127.0.0.1:8972/>。首次使用建议先自检：

```bat

```

`run.bat` 会依次找 `.venv\Scripts\python.exe` → `python` → `py -3`，任意一个 Python 3.9+ 都行。

想装成命令行工具（可选，会生成 `iabot` 命令）：

```bat
pip install -e .

```

```bat

python -m iabot analyze btc --mode swing
python -m iabot analyze BTC-USDT --json --brief
python -m iabot analyze BTC-USDT --save     :: 分析后把这条信号写入历史库
python -m iabot scan BTC-USDT,ETH-USDT,SOL-USDT   :: 批量扫描，按信号强度排序
python -m iabot scan all --top 40            :: 全市场扫描（自动筛出流动性达标的加密币）
python -m iabot scan all --radar            :: 只看全市场雷达表，不做深度分析（1 个请求）
python -m iabot scan all --save             :: 扫描并把有方向的信号写入历史库
python -m iabot backtest BTC-USDT --mode swing   :: 历史回测，统计胜率与期望值
python -m iabot backtest BTC-USDT --save         :: 回测并把参数+结果存档（可事后复现/对比）
python -m iabot backtests --symbol BTC-USDT      :: 查看历史回测记录与参数差异
python -m iabot watch                             :: 终端监控：循环扫描，信号变化时提示（Ctrl+C 退出）
python -m iabot analyze BTC-USDT --paper          :: 分析后直接开一笔模拟仓
python -m iabot backup                            :: 备份信号数据库（信号/持仓/回测/利润簿）
python -m iabot check                  :: 网络 / 证书 / 行情接口 / 配置体检
python -m iabot notify-test           :: 发一条测试通知，验证 notify 渠道配置
```

`analyze` 也接受简写：`python -m iabot btc`。

常用参数：

| 参数 | 说明 |
|---|---|
| `--mode intraday\|swing` | 波段（默认，持仓数天~数周）或日内（持仓数小时；实测负期望，不建议实盘） |
| `--equity 450` | 账户权益 USDT，覆盖配置 |
| `--leverage 10` | 杠杆倍数，覆盖配置 |
| `--risk 2` | 单笔最大亏损占账户百分比 |
| `--save` | 把本次分析结果写入信号历史库（SQLite，默认 `data/signals.db`） |
| `--json` / `--brief` | 输出原始 JSON / 不打印因子明细 |

`scan` 常用参数：

| 参数 | 说明 |
|---|---|
| `all` / `全部` | 扫全市场；可与具体合约混写（`BTC-USDT,all`） |
| `--top 40` | 全市场深挖多少个（按排序取前 N） |
| `--min-turnover 100000` | 24h 成交额下限（USDT），过滤僵尸合约 |
| `--all-assets` | 连代币化股票 / 大宗商品一起扫（默认只扫加密币） |
| `--sort turnover\|abs_change\|change` | 候选排序：成交额 / 24h 波动 / 24h 涨跌 |
| `--workers 4` | 并发分析数（调高容易撞火币限流） |
| `--radar` | 只打印全市场雷达表，不做因子打分 |

`backtest` 常用参数：

| 参数 | 说明 |
|---|---|
| `--mode swing` | 回测模式（日内按 15min、波段/超卖反弹按 1day 重放） |
| `--bars 300` | 取多少根主周期 K 线做历史 |
| `--step 3` | 每隔多少根构造一个建仓点（越小越密越慢） |
| `--json` | 输出含 R 权益曲线的原始 JSON |

## 全市场监控

关注列表只有 10 个币，怎么盯住**所有**币？两段式：

1. **广度雷达（1 个请求）**：`batch_merged` 一次拿回交易所全部 400 个 USDT 永续的现价、
   24h 涨跌、成交额；`swap_contract_info` 补上面值与标签，合成一张全市场表。
   网页上就是"全市场雷达"面板，CLI 是 `scan all --radar`。
2. **深度分析**：只对筛出来的候选做完整因子打分。筛选规则在 `universe` 配置块里。

### 为什么不全量深挖

全量 400 个合约每个要 10 个接口，4000 次请求；而且流动性差异极大：

| 合约数 | 24h 成交额 |
|---|---|
| 388 | 全部 USDT 永续（含股票类） |
| ~130 | 纯加密币 |
| 170 | ≥ 10 万 U |
| 23 | ≥ 100 万 U |

成交额中位数只有 **6.5 万 U**，一半合约是几乎没有流动性的僵尸盘——深挖它们既慢又必然被限流。
所以默认口径是「加密币 + 24h 成交额 ≥ 10 万 U + 取前 N 个」，把有限的请求花在能真下的单上。

### 过滤规则（`config.json` 的 `universe`）

| 字段 | 默认 | 说明 |
|---|---|---|
| `enabled` | 关闭 | 是否启用全市场模式（网页/CLI 可临时开，不依赖它） |
| `asset_class` | `crypto` | `crypto`=剔除代币化股票/大宗商品/指数；`all`=全都扫 |
| `min_turnover_usdt` | 100000 | 24h 成交额下限，过滤僵尸合约 |
| `min_price` | 0 | 现价下限，过滤近零价合约 |
| `include_labels` / `exclude_labels` | 空 | 按交易所标签增减。`include_labels` 是"白名单式捞回"：命中标签的合约豁免流动性门槛，排在正常候选之后但**为其预留名额**，不会被 `max_symbols` 截掉 |
| `include` / `exclude` | 空 | 强制纳入 / 排除；`include` 优先级最高（置顶），同样豁免流动性门槛 |
| `max_symbols` | 60 | 深挖上限 |
| `sort` | `turnover` | `turnover` / `abs_change` / `change` |

### 定时任务：分批轮转，不是每轮全扫

勾上「全市场轮询」后，每轮只深挖 `batch_size` 个（默认 20），游标跨轮推进，
全市场转完一圈才回头。这样 130 个币 ÷ 20 = 7 轮轮完，每轮约 50 秒，间隔 300 秒完全跑得动；
也永远只请求 `batch_size × 10` 个接口。设 `batch_size ≥ 全市场数量` 就退化成每轮全扫。

并发数 `workers` 默认 4。实测 8 个合约串行 80.8 秒、并发 4 只要 20.5 秒（快 3.9 倍）；
再往上调收益有限，火币对高频请求会限流（429），程序会指数退避重试。

### 用法

```bat
python -m iabot scan all --radar                    :: 全市场雷达表
python -m iabot scan all --top 40 --save            :: 全市场深挖 + 落库
python -m iabot scan all --min-turnover 1000000     :: 只扫百万 U 以上的大币
python -m iabot scan all --sort abs_change --top 20 :: 扫今天波动最大的 20 个
python -m iabot scan BTC-USDT,all                   :: 指定合约 + 全市场混合
```

网页上：「全市场雷达」面板可调筛选条件并点任意一行跳转分析；「扫描全市场」走并发深挖；
「定时任务」里勾「全市场轮询」设每轮深挖数。

## 网页控制台

- **选币种**：输入框支持任意 `XXX-USDT`，带 80+ 币种中文名/别名下拉；下面还有常用币快捷标签。
- **全市场雷达**：一次请求拉回交易所全部 USDT 永续，按流动性/类别筛选后列出现价、24h 涨跌、成交额与已有信号，点任意一行跳转分析。
- **全市场轮询**：定时任务可切到全市场模式，每轮深挖一批、游标跨轮推进。
- **模式**：日内 / 波段 / 超卖反弹，切换即重算。
- **账户参数**：权益、杠杆、单笔风险，改动立即重算仓位（不写回配置）。
- **行情与关键位**：手绘 K 线（周期可切 1min/5min/15min/60min/1day…），叠加 MA20、成交量、入场区、止损与止盈位。
- **关键价位阶梯**：右侧阻力、左侧支撑，权重条越长越重要（摆动高低点、成交量密集区、斐波那契、均线、整数关口、盘口挂单墙的综合结果）。
- **交易建议**：方向 / 评分 / 置信度 / 入场区间 / 止损 / 止盈列表（含每档预计盈利 U）/ 张数 / 保证金 / 盈亏比 / 风险提示。
- **因子明细**：10 项因子的得分、权重、贡献和文字依据，评分怎么来的看得见。
- **定时任务**：勾选"启用循环执行"，填间隔秒数和合约列表，保存后后台线程开始轮询；可随时"立即执行一轮"。运行日志与历史信号通过 SSE 实时推送到页面。
- **多币种速览**：一键扫描关注列表，按 |评分| 排序，点任意一条跳到该币分析。顶部有市场情绪条（多空占比）。
- **信号胜率**：定时任务跑过的信号会被回填结局（先到目标还是先碰止损），按评分档/模式/置信度/币种/生效方案统计胜率与平均 R。
- **因子权重调参**：网页上拖动 10 个因子的权重滑块与评分阈值，保存到 `config.json`，配合回测与胜率统计找最优组合；可开启"多周期共振"第 11 因子。
- **参数方案**：把"权重+阈值+模式"打包成命名方案，对同一段历史逐个回测对比期望 R，一键应用到实盘扫描与定时任务。胜率面板按方案分组，实测验证哪个方案真的准。
- **模拟盘持仓**：手动录入或从分析结果**一键开模拟仓**（自动填入场/止损/止盈/张数）；自动跟踪浮动盈亏，被止损/止盈打掉时自动平仓记录；现价逼近止损时推送预警。带**利润簿**：已平仓盈亏按周/月/总汇总、胜率、权益曲线（扣手续费）。
- **通知**：配置 Telegram / Bark / 通用 Webhook 后，方向翻转与强信号实时推送（`config.json` 的 `notify` 块）。
- **导出报告**："导出报告"按钮打开一页自包含 HTML（内联 SVG K 线 + 建议 + 胜率 + 因子），浏览器打印即可存成 PDF，便于存档分享。

网页上改定时任务、因子权重和参数方案会写回 `config.json`，重启后依然生效。

## 回测与成本

`python -m iabot backtest BTC-USDT --mode swing` 在历史 K 线上滑动回放：每隔若干根
构造一个"当时的快照"（只用该点及之前的数据，无未来函数），走真实的打分与两道闸门，
再用后续 K 线判定结果。

每笔交易都会扣三项成本，全部折算成 R（成本占单笔风险的比例）：

| 成本 | 怎么算 |
|---|---|
| 手续费 | `taker_fee_bps × 2 × (名义/风险)`，开平各一次 |
| 滑点 | `slippage_bps × 2 × (名义/风险)`，开平各一次 |
| 资金费 | 按**持仓时长**累计：费率 × (持仓小时 / 8) × (名义/风险)；费率为正时多头付、空头收 |

资金费用的是**每个建仓点当时生效的费率**（取自 HTX `swap_historical_funding_rate`
历史序列），不是拿"当前费率"套全部历史——后者在费率剧烈波动的行情里会让回测严重失真。

参数在 `config.json` 的 `analysis.backtest` 里（费率、滑点 bps、是否计资金费）。
输出里的"期望 R"已扣成本，正数才代表长期按规则做有优势；同时会按你的账户权益和单笔
风险折算出金额（`--equity` / `--risk` 可覆盖）。

### 回测实验记录

`backtest --save` 会把这次回测存成一条实验记录，网页和 `backtests` 命令都能看。
关键在于**存的是完整参数快照**（权重、阈值、共振开关、成本参数、步长、账户口径），
而不只是一个模式名——这样几个月后能复现那次结果，也能并排对比：

```
$ python -m iabot backtests
  #3  BTC-USDT  intraday   胜率 60.0%  期望 +0.412 R  24 笔  期末 520 U
  #2  BTC-USDT  swing      胜率 55.0%  期望 +0.180 R  11 笔  期末 466 U

  与上一条相比改了：
    - 模式: swing → intraday
    - 权重 momentum: 0.15 → 0.4
```

网页上"参数方案"卡片里勾选"回测时存档"，做方案对比时会一次性把每个方案的结果都记下来。

## 它是怎么算的

### 因子与权重

| 因子 | 权重 | 看什么 |
|---|---|---|
| 波动率 | 0.30 | 当前 ATR% 在自身近 250 天中的百分位（越低越多） |
| 成交量 | 0.18 | 成交量 z-score 相对前 20 日均值（放量偏空） |
| 日线趋势 | 0.10 | 价格 vs SMA20/50/200、EMA12/26 |
| 资金费率 | 0.08 | 费率相对自身 30 日均值的偏离（过热反向） |
| 大户持仓 | 0.06 | 大户多空净比相对自身基线的偏离（σ） |
| 持仓量 | 0.06 | OI 变化与价格方向是否共振 |
| 动量 | 0.06 | RSI、近期涨跌幅（弱反向） |
| 摆动结构 | 0.05 | 分形高低点是否抬高/降低 + ADX 判趋势市/震荡市 |
| 1小时趋势 | 0.04 | 价格 vs SMA20/50、MACD 柱状 |
| 盘口深度 | 0.04 | 买卖挂单墙的偏向 |
| VWAP | 0.03 | 现价相对当日成交量加权均价 |

> 权重来自样本外检验，不是手感。检验方法和结论见下面
> 「哪些信号真的有预测力」。趋势类因子给了低权重，是因为它们的
> IC 符号在训练/测试两段里会翻转，**无法用于定方向**，只能当参与项。

> 旧版的一个硬缺陷：因子函数里的权重和 `FACTOR_DEFAULTS` 各自写死一份，
> 实际生效的是函数里那份，改配置不动行为。现已统一由 `_w(name)`
> 单点读取，并在 `compute_factors` 末尾做一次归一化。

加权平均天然向 0 收缩（因子经常互相抵消），所以评分用
`score = 100 · tanh(加权均值 / 0.40)` 压缩：中间区域放大，极端区域饱和。
`|score| ≥ 30` 才给方向，否则观望（超卖反弹模式除外——它走独立判据，不评分）。

### 哪些信号真的有预测力

把每个因子单独拿出来做 IC 检验（19~23 币 × 1000 根日线，**按时间切成 60/40**，
前半定方向后半验证）。结果是：

| 因子 | 训练段 IC | 测试段 IC | 结论 |
|---|---|---|---|
| 波动率 `atrp` / `hl` | + | + | **稳定可用** |
| 成交量 `volz` | + | + | **稳定可用** |
| MACD 反向 | + | + | 弱，可用 |
| 日线/1小时趋势 | − | + 或 0 | **符号翻转，不可用** |
| RSI | − | + | **符号翻转，不可用** |
| 摆动结构 | − | + | **符号翻转，不可用** |
| VWAP | − | 0 | **符号翻转，不可用** |

趋势类因子训练段 IC 是负的、测试段转正或归零——**方向在样本外根本不可靠**，
把它们压到低权重当"参与项"而不是"方向源"。

真正稳定的是**低波动**：把币按当前 ATR% 分三档，**低波动档在两个时间段都多赚**

| ATR% 分档 | 前半段 6 日收益 | 后半段 6 日收益 |
|---|---|---|
| 低 | **+0.75%** | **+0.72%** |
| 中 | +0.31% | +0.34% |
| 高 | +0.02% | +0.00% |

稳定子集（波动率 + 成交量 + MACD 反向）合成的复合信号：
训练 IC +0.035 / 测试 IC **+0.026**，命中率 **52.1% / 51.5% / 51.8%**，
两段都过半。所以波动率和成交量拿到了最高的两个权重。

`_f_volatility` 和 `_f_volume` 都是**相对自身历史**的百分位/z-score，
不是绝对值——同一套阈值在 BTC 和山寨币上语义完全不同，
用绝对阈值必然一头饱和（旧版 `_f_elite` / `_f_funding` 就是这个毛病：
用绝对净比和绝对费率，结果 39/40 个币全在 ≤0 的同一侧，因子退化成常数偏空）。

### 这个评分的方向预测能力依然很弱

**不是反向，是接近无效。** 完整 `build_plan` 的命中率（时序切分）：

| 模型 | 训练段 | 测试段 |
|---|---|---|
| 旧权重 | 46.9% | 53.6% |
| 新权重 | 48.4% | **53.6%** |

测试段完全一样。**命中率由市场状态决定，不由权重决定**——换权重救不了它。
新模型的改善在于：横截面一致性从"18 个看空 1 个看多"的常数偏空，
变成跟市场同步（实测一次扫描 15 个空 / 0 个多，15 个方向全部正确）。

所以别把"方向"当预测用。它更像一个"该往哪边挂单"的过滤器，
正期望来自盈亏比结构，不来自方向判断。

### 跌段做多为什么修不掉，以及另开的一条通道

多因子模型在跌段里做多是亏的（20 币 × 2060 建仓点、5 日持有、时序切分 60/40）：

| 区段 | 基准上涨率 | long 命中 | short 命中 |
|---|---|---|---|
| train（跌段） | 43.1% | 41.3% | **57.0%** |
| test（涨段） | 52.7% | **52.7%** | 50.4% |

试过五种修法，全部失败：

| 候选闸门 | 结果 |
|---|---|
| price vs SMA 锚拦 long | 上方 42.6% / 下方 40.9%，无差异 |
| 状态与趋势同向才开仓 | 涨段 short 53.9% → 44%，砍掉唯一正 edge |
| 纯趋势跟随 | 同上 |
| long 需趋势确认（不对称） | 涨段 long 55.0% → 50.5%，整体 47.6% → 46.9% |
| 按 plan.rr 分桶 | 跌段 long 亏损均匀铺开，不在任何 rr 档集中 |

原因不是"没调好"，是**edge 本身不对称**：做空在两个区段都赚，做多只在涨段赚。
任何"拦一边"的闸门都是用一侧 edge 换另一侧，数据里不存在"跌段接飞刀还赚"的 alpha。

所以没有去加第七个闸门，而是承认缺一个策略，另开一条通道——**超卖反弹**
（`--mode reversion`）：跌势里跌透了，博 1~2 天回抽，目标位就是回到 SMA20。

触发三条缺一不可：`RSI(2) < 10` 且 `close < SMA20×1.03` 且 `close < SMA200`。
只做多（反弹没有空头对应物，跌势追空归波段）。

#### 这条通道的定位：无 edge，不建议实盘

**先说两处被更正的错误。** 这个通道的第一版提交写过"留出法 train/test 都是
65.6%"，那是错的：每币日线默认只取 300 根，SMA200 一成立就只剩约 95 天可评估，
所谓"前 60% 训练段"是个**空集**——拿空集当验证不是验证。
放回完整历史重测（同一批 20 币、同一套真实规则，含手续费/滑点/资金费）：

| | 样本 | 期望 R | 95% 置信区间 | 分区制 |
|---|---|---|---|---|
| **swing（主）** | 5418 | **+0.184R** | [+0.150, +0.217] | 三区全正 |
| reversion | 752 | −0.384R | [−0.478, −0.285] | 20 个币全负 |

更根本的是 reversion 的**原始前向收益本来就是 0**（1/2/3 日：+0.08% / −0.01% /
+0.06%），只有 2025-2026 为正、2021-2022 熊市为负。0% 的原始信号扣掉成本必为负，
所以不是出场设计能救的——**信号本身没有 edge**。之前那个 +0.367R 是"最近三个月
恰好顺手 + 两个币撑起来"的样本假象。

**决定**：reversion 判为无 edge，**不建议实盘**。代码保留供研究（触发逻辑
本身干净，换市场仍可复用这套框架），默认不启用，定时任务也不接受这个模式，
且任何输出都会附带"不建议实盘"的警告。

#### 样本量：默认值从 300 根改成 2000 根

上面所有结论被推翻的根因，是 `analysis.kline_size` 默认只取 300 根。
接口实际上限是 2000 根，取满才有可用的样本：

| `kline_size` | 日线覆盖 | 15min 覆盖 |
|---|---|---|
| 300（旧默认） | 0.82 年 | 3.1 天 |
| 2000（新默认） | 5.48 年 | 20.8 天 |

抓取耗时几乎不变（各周期并发请求，瓶颈是网络往返不是数据量）：

| kline_size | 实测耗时 |
|---|---|
| 300 | 7.4s |
| 1000 | 4.0s |
| 2000 | 4.7s |

所以现在默认取满接口上限，`config`、`Advisor`、`MarketClient.snapshot`、
网页回测、CLI `--bars` 五处的默认值统一为 2000，并用测试锁死。
实测效果（swing，20 币）：单币样本从 4~10 笔涨到 70~120 笔，
合计 1735 笔、单笔期望 +0.207R、胜率 51.0%——方向结论没变，但数字终于有
统计意义了。

#### 残缺样本不再静默出结果

某个周期抓取失败时，`Snapshot` 只把那几根丢掉、记进 `errors`，回测照常用
剩下的数据跑出一个**看起来正常**的数字——这是最危险的失败模式。实测 AVAX
有一轮日线返回空数组，跑出 0 笔交易，而 `missing_periods` 是空的（空响应
根本没被记录）。

现在两处都堵上了：空响应在 `market.snapshot` 里记成 `kline:<周期>: empty
response`；回测只要发现任何周期缺失或过短（<2 根），直接标
`insufficient_data=True`、不出任何期望值，CLI 退出码 1、网页返回 422。
另外 `backtest_all` 里数据不足的方案排到最后——期望值 0 不该被当成
"最好的方案"。

#### 但这条死路换来了一个真修复：趋势否决闸门

查 reversion 时意外量到了 swing 的真实浪费点——**逆势 long**：

| 原样 | 5415 | +0.183R |
| 　其中 long | 2799 | **+0.119R** ← 拖后腿的在这 |
| 　其中 short | 2616 | +0.252R |
| 只保留与日线趋势同向 | 2941 | **+0.199R** |
| 　其中 long | 1199 | **+0.165R** |
| 　其中 short | 1742 | +0.222R |
| 被砍掉的逆势单 | 2474 | +0.165R |
| 　其中逆势 long | 1600 | **+0.085R**（2021-2022 是 −0.002R） |
| 　其中逆势 short | 874 | +0.312R |

逆势 short 反而赚（+0.312R），该砍的只是"**下跌里做多**"。之前五种闸门在 300 根

实现是**否决权**而不是"把趋势提成方向源"：方向仍由状态因子 + 趋势确认因子决定，

也就是它仍然是"拿手数换质量"，不是无条件更好。**保持关闭**，但结论从

### 怎么验证一个策略：三件事一起看

到这一步已经能算出"整段历史上期望多少 R"，但**光看这个数会被骗三次**。
项目里被坑过的每一种，都对应下面的一个检查：

| 要防的骗法 | 检查 | 怎么做的 |
|---|---|---|
| 点估计是运气 | 置信区间 | 自助法重采样每笔 R，给 95% 区间；区间跨 0 就不能说有 edge |
| edge 只来自某一段行情 | 折间一致性 | 把历史切 N 折逐折回测，看正收益折占比 |
| edge 只来自某几个币 | 收益集中度 | 跨币合并，算前 2 个赚钱标的占正 R 的比例 |

三个都有对应的入口：

```
iabot backtest BTC-USDT --wf 5     # 单币折间检验
iabot validate                      # 20 个主流币，整段 + 折间 + 集中度
```

`validate` 的实际输出（swing，20 币 × 5 折，2026-10）：

```
合并        : 1865 笔  胜率 48.5%  期望 +0.1458R  95%区间 [+0.088,+0.207]
折间一致性  : 正收益折 68/100（68%）  合并 +0.1572R
收益集中度  : 19 个赚钱标的，前 2 个占正 R 的 20%（APT、ATOM）
组合模拟    : 1030/1865 笔入场（并发上限 5 挡掉 835 笔）  收益 +3674.3%  最大回撤 49.2%
! 并发上限 5 挡掉了 835 笔（45%）：单笔期望不等于组合能拿到的收益
! 组合最大回撤 49%：单笔风险 +0.208R 掩盖了这个尾部
结论        : 有保留
```

前三个都过了，**第四项把结论从"通过"拉回"有保留"**——这正是加组合模拟的原因：

- 单笔期望是按币独立算的，假设每笔都有满额资金。真实账户只有一个，
  并发上限 5 时 **45% 的信号根本做不上**。
- 山寨币高度相关，"同时 5 个多头"约等于一个 5 倍杠杆多单，
  组合最大回撤 **49%**，远比单笔 +0.146R 看起来凶险。
- `+3674%` 是复利口径（每笔按当前权益的 2% 下注，1030 笔滚出来的），
  只作参考；真正该看的是**回撤**和**被挡掉的单量**。

四项都过才叫"通过"。对照 reversion 当年的形态：正收益折只有 40%、前 2 个币
占正 R 的 52%——单看"整段 +0.367R"完全看不出来。

#### 限什么，比限多少更重要

第一版的组合模拟只限了"同时最多几个仓"（默认 5），结果 45% 的信号做不上、
最大回撤 49%。改成**限总热度 + 限相关性簇**之后，同样的 20 币：

| 约束 | 做上 | 挡掉 | 最大回撤 |
|---|---|---|---|
| 只限仓位数 5 | 1030/1865 | 835（并发） | **49.2%** |
| 仓位数 8 + 热度 12% + 同簇 3 | 1105/1865 | 567（热度）+ 193（同簇） | **14.2%** |

**做上的单更多，回撤只有原来的三分之一。** 原因很直白：限"几个仓"限的是
数量，而不同币的止损宽度不同、风险金额并不相等；山寨币又高度相关，
"5 个仓"约等于"1 个 5 倍仓位"。真正该限的是**风险总额**和**同向暴露**。

所以 `validate` 的默认约束现在是：仓位数 8（兜底）+ 热度 12% + 同簇 3。
相关性簇用日线收益的皮尔逊相关系数算（阈值 0.7，并查集连通分量）。

#### 但得确认："挡掉的是不是好单？"

上限挡掉 40% 的信号，如果被挡的反而更好，那就是在拿收益换安全。所以
`portfolio_backtest` 现在也统计被挡单子的期望，和做上的直接对比：

```
组合模拟    : 1083/1749 笔入场  收益 +5593.9%  最大回撤 23.4%
挡单质量    : 做上的 +0.221R vs 挡掉的 +0.124R —— 挡对了（挡掉的是较差的一批）
```

20 币实测：**被挡掉的单子期望只有做上的一半**，说明这些上限筛掉的确实
是较差的一批，不是白扔收益。差距在 ±0.05R 以内时结论会写成"差距不大
（上限主要在控风险，不是在挑单）"，不会硬说挡对了。

#### 但评分本身没有排序能力

把所有交易按 |评分| 分三档看期望，结果**不单调**：

| 档位 | |评分| 区间 | 笔数 | 期望 R |
|---|---|---|---|
| 低分 1 | 30–40 | 619 | +0.174 |
| 低分 2 | 40–55 | 618 | **+0.288** |
| 高分 | 55+ | 619 | **+0.111** |

中间档最好，最高档反而最差。再按"每笔的主导因子"分组，答案很清楚：

> **更正（重要）**：这一节和三档表的结论是**两个 bug 造成的假象**，
> 已经作废。作废原因和修正后的结论见
> 「评分终于有了排序能力」。原文保留是为了留下痕迹——
> 它不是被新实验推翻的，是被发现"当时测的是另一个东西"。

```
主导因子: 趋势日线 1465 笔 +0.215R | 成交额 325 笔 +0.153R | 波动率 66 笔 -0.145R
```

**旧原文（作废）**：评分几乎就是**日线趋势因子**的单一映射（79% 的单子
由它主导）。所以"高分档更差"翻译过来是：**日线趋势越极端，越可能是行情的
尾声**。这直接影响一个旧结论：把阈值从 30 往上调，不是在"挑更高质量的
单"，而是在**主动选中更差的那一档**。

同一个窗口下多空拆分是 **long 999 笔 +0.282R / short 857 笔 +0.086R**，
和"空单更好"的历史结论相反。这正说明为什么 `risk_mult_*` 默认保持 1.0、
为什么要有影子账户：**方向优势会随行情翻转，不能当常数。**

**试过的修法（无效，保持关闭）**：对 |日线趋势| 超过 0.6 的部分做衰减
（`analysis.trend_dampen`），想削掉极端读数。12 币实测：

| at0.5 k0.5 | +0.2097 | +0.200 / +0.250 / +0.180 |
| at0.7 k2 | +0.2108 | +0.182 / +0.301 / +0.149 |

期望没变、分档依然不单调。说明问题不在"分数太高"，而在中间那档恰好是
甜点区——单纯压分数不会把交易挪出最差的那档。选项保留（默认关）是为了
以后换参数重测，不是因为它有用。

| 8 仓 + 热度 12% + 簇 3 | 24.4% | 19.8% | +7447% vs +6162% |
| 5 仓 | 26.4% | 23.6% | +9465% vs +8987% |
| 5 仓 + 热度 10% + 簇 2 | 26.4% | 25.2% | +2833% vs +2986% |
| 12 仓 + 热度 20% + 簇 4 | 21.6% | **21.6%** | +18397% vs +20251% |

前两套变好、后两套持平或变差，**不是一个稳定效果**，就是路径运气。
`trend_dampen` 保持关闭。

#### 评分终于有了排序能力：两个 bug 的更正

顺着"闸门漏斗"里最大的一项（27% 评不出方向）往下查，最后挖出两个 bug。
它们一起**掩盖了评分的排序能力**，前面几节基于"高分档最差"推出的一整套
结论（分数带、趋势衰减、阈值无效）全部建立在错的前提上。

##### bug 1：funding 因子有 lookahead

`_slice_snapshot` 切历史快照时，K 线、持仓量、大户持仓、资金费**历史**
都按时点切了，唯独 `funding_rate` 这个"当前值"一直沿用**今天**的。
而 `_f_funding` 在没有历史样本时会退回"按当前费率水平给分"的分支，
于是每个历史检查点都拿到一个**来自未来的、固定的强投票**（±0.45/±0.9）。
它在 `state_names` 里，权重 0.08，直接参与"决定观点"的那一侧。

修法：`funding_history` 为空时把 `funding_rate` 置 `None`，让因子按"无数据"
处理（0 分），而不是拿一个未来值充数。

##### bug 2：对外显示的评分不是决定方向的评分

- 阈值判的是 `dir_score`：状态因子（波动率/成交额/资金费）定观点，
  趋势因子只做确认，`state + 0.5×trend` 加权。
- 但 `plan.score`（网页、CLI、评分排序诊断都用它）是**11 个因子的加权平均**。
两个是不同的数，实测 24 个币里 **9 个出现"评分 −84 却观望"**。

修法：`plan.score = dir_score`；11 因子平均值单独存
`plan.score_all_factors`，只在需要时参考。

##### 修完之后：排序能力出现了

| 指标 | 修前 | 修后（5 折） |
|---|---|---|
| 成交 | 1525 | 1930 |
| 单笔期望 | +0.181R | **+0.243R** |
| 95% CI | [+0.118, +0.246] | [+0.190, +0.294] |
| 胜率 | 50.3% | **55.7%** |
| 正收益折 | 55/80 | **94/115** |
| 评分分档 | +0.169 / +0.286 / **+0.087**（不单调） | **+0.149 / +0.233 / +0.347**（单调） |

分档单调递增，且高低档差 +0.198R——这才叫"分数有排序能力"。

##### 因此把阈值 30 调到 40

以前"调高阈值会选中最差那档"，现在反了。组合层面实测（24 币，8 仓 +
热度 12% + 簇 3）：

| 阈值 | 信号 | 执行 | 单笔期望 | 组合期望 | 收益 | 回撤 |
|---|---|---|---|---|---|---|
| 30 | 1868 | 1085 | +0.236R | +0.258R | **+14330%** | 11.9% |
| **40** | 1659 | 1043 | +0.255R | +0.255R | +10614% | 14.7% |
| 50 | 1395 | 929 | +0.260R | +0.252R | +5866% | 16.9% |
| 60 | 1100 | 778 | +0.308R | +0.296R | +5915% | 14.7% |
| 70 | 763 | 596 | +0.375R | +0.354R | +4596% | **6.1%** |

**收益最高的是 30，胜率和单笔质量最高的是 70**。这是典型的手数/质量
权衡，没有免费午餐。选 40：单笔期望 +8%、回撤没变差多少、收益只降 26%，
比 30 更稳；再往上就开始拿收益换质量，不符合"要加单"的原则。
（想要更低回撤就用 60–70，但那是另一个风险偏好，不该做成默认。）

#### 分数带闸门：已删除

> **整个功能已从代码里删掉**，理由见下。下面保留的是当时的实验记录，
> 用来解释为什么"看起来很稳的结论"也会整体作废。

它建立在"高分档最差"这个前提上，而那是 bug 造成的假象（见
「评分终于有了排序能力」）。修完之后高分档才是最好的（+0.347R vs
低分档 +0.149R），所以"排除高分"等于**砍掉最好的那批**。

在修正后的评分上重测（24 币，锁死同一批快照，逐币配对）：

| 配置 | 成交 | 单笔期望 | Δ期望 正的币 | Δ期望中位 |
|---|---|---|---|---|
| baseline（阈值 40） | 1526 | +0.2425R | — | — |
| 带 40–55 | 389 | **+0.1411R** | 6/22 | **−0.115R** |
| 带 45–70 | 724 | +0.1807R | 6/22 | −0.047R |

两个区间都显著变差，逐币也几乎一致变差。所以不是"调参数能救"，
是方向错了——删掉，不留开关（留着只会是个诱人但有害的陷阱）。

下面是当时的实验记录：

既然"分数越高越好"不成立，就改成**只接受 |评分| 落在甜点区间内的信号**
（`analysis.score_band`）。难点是区间不能在同一批数据上挑完就算，所以做了
前后半段分离检验：前 60% 挑区间，后 40% 验证。

18 币 × 2000 根日线：

| 配置 | 前半段（挑区间） | 后半段（验证） |
|---|---|---|
| 无闸门 | 1035 笔 +0.203R | 667 笔 +0.154R |
| 带 45–60 | 282 笔 +0.347R | 163 笔 **+0.214R** |
| 带 40–55 | 262 笔 +0.226R | 153 笔 **+0.316R** |
| 带 35–55 | 345 笔 +0.238R | 196 笔 **+0.290R** |

**带区间的规则在两段都稳定优于无闸门**，说明排除最高档这件事本身是真实的，
不是拟合出来的。只封顶（不设下限）则不稳定（前半段 +0.171R，反而变差），
所以不能图省事。

但**具体边界在两段之间会漂**（前半最优 45–60，后半最优 40–55），这是典型
的过拟合残留。所以区间取两段都有效的 **40–55**，并且——

- 默认关；
- 规则本身（排除最高档）用 `validate` 的评分排序诊断持续监控，不再凭
  单次回测调边界；
- **不进默认影子列表**：组合回测证明它不值得（见下节）。

完整 18 币 × 5 折（每币 5 段，约 1525 笔）的核验结果：

| 配置 | 笔数 | 期望 R | 95% CI | 正收益折 | 胜率 | 评分分档是否单调 |
|---|---|---|---|---|---|---|
| 无闸门 | 1525 | +0.181 | [+0.118, +0.246] | 55/80 | 50.3% | **否** |
| 带 40–55 | 373 | **+0.237** | [+0.102, +0.376] | 54/80 | 51.1% | **是** |

三件事同时看才敢下结论：

1. **期望提高 31%**（+0.181 → +0.237）；
2. **折间一致性没掉**（55/80 → 54/80，都是约 68%）；
3. **评分分档重新变单调**——无闸门时是 +0.169 / +0.286 / +0.087（高分档最差），
   开闸门后是 +0.194 / +0.211 / +0.305（高分档反而最好）。排序能力被修好了。

代价也要说清楚：交易数从 1525 降到 373（少 76%），样本变少，CI 变宽
（[+0.102,+0.376] 对 [+0.118,+0.246]）。省下来的钱要靠更少的手续费和
更小的回撤补回来——**这部分实测没有补回来**。

##### 组合层面：单笔变好，账户变差

单笔期望 +31% 不等于账户多赚钱。18 币、同一套组合上限、只让分数带这一个
变量变化，按复利模拟 450U 账户：

| 组合上限 | 无闸门 | 带 40–55 |
|---|---|---|
| 5 仓 | 1689 信号，执行 992，单笔 +0.249R，收益 **+6820%**，DD 19.9% | 404 信号，执行 392，单笔 +0.259R，收益 +501%，DD 36.7% |
| 8 仓 + 热度 12% + 簇 3 | 执行 1052，单笔 +0.218R，收益 **+4472%**，DD 18.6% | 执行 385，单笔 +0.245R，收益 +429%，DD 39.5% |
| 5 仓 + 热度 10% + 簇 2 | 执行 891，单笔 +0.209R，收益 +2329%，DD 44.1% | 执行 354，单笔 +0.267R，收益 +450%，DD 33.8% |

**三种上限下结论一致**：单笔期望确实更高，但收益差 5–14 倍，回撤也没
系统性变小。原因不神秘——450U 的小账户靠的是**手数**，信号数从 1689
砍到 404，机会密度不够了；而复利下"少交易"省下的手续费远抵不过少赚的
利润。加上 400 笔样本的统计噪声本来就大，**这个闸门不值得开**。

它现在的状态是：默认关，不在默认影子列表里（每轮多算一遍，收益不配），
但 `band_40_55` 方案保留在 `VARIANTS` 中，需要时可手动
`python -m iabot shadow --variants base,band_40_55` 单独跑。

**这一轮真正的教训是：单笔期望和账户收益是两个问题，前者变好不代表后者
变好。** 排序能力修好了，但那不是赚钱的瓶颈——手数才是。

##### 由此得到一条通用规则：别用"质量闸门"筛单

无闸门时三档的期望是 **+0.169 / +0.286 / +0.087——全为正**。也就是说
被分数带筛掉的每一档，期望都是正的。筛掉它们等于**拿确定的正期望去换
不确定性**，无论单笔统计多好看。

所以：

- **质量闸门**（按分数/趋势筛掉信号）在这个策略上先天吃亏——`trend_veto`、
  `trend_dampen`、分数带，三次都是同一个原因失败；
- **风险上限**（最多几仓、热度、相关性簇）不筛质量，只控暴露，**这些是赚的**
  ——被它们挡掉的单子期望只有 +0.10R，比执行的 +0.22R 差，但换来的是
  DD 从 49% 降到 14%；
- 想提升账户收益，正确的方向是**找到更多正期望的setup**（更多标的、
  更多周期、更多入场条件），而不是在现有信号里挑得更细。

> **这条规则需要修正**：三次失败都是"在错的分数上测的"。修完两个 bug
> 之后评分有排序能力了，提高阈值（一个质量闸门）确实能同时提高胜率和
> 单笔期望。但"要加单不要减单"依然成立——收益最高的仍是手数最多的
> 阈值 30。修正后的表述：**质量闸门能改善单笔质量，但会减少手数；
> 要不要用，取决于你要收益还是要回撤，没有免费的改善。**

一句话：**要加单，不要减单。**

##### 把规则用起来：扩标的池，并默认打开全市场轮询

规则说完要落地。最直接的加单来源是**标的池**——原来默认只盯 `BTC-USDT`
（`schedule.symbols` 只有一个，`universe.enabled=false`）。

实测：18 币扩到 28 币（新增 BCH/ETC/FIL/ALGO/XLM/AAVE/CHZ 等），
同一套组合上限（8 仓 + 热度 12% + 相关性簇 3），450U 复利：

| 口径 | 信号 | 单笔期望 | 执行 | 组合期望 | 收益 | 回撤 |
|---|---|---|---|---|---|---|
| 18 币 | 1690 | +0.189R | 1043 | +0.217R | +4245% | 20.2% |
| 28 币 | 2396 | **+0.207R** | 1198 | **+0.237R** | **+12349%** | **14.2%** |

**四个指标同时变好**——收益 2.9 倍，而单笔期望和回撤反而都改善了。原因
是相关性簇限制：加进来的币彼此不同步，簇上限自动把暴露摊平，于是"更多单"
没有变成"更大回撤"。

新增币的表现（笔数 / 期望R）也验证了这不是靠老币扛着：

| 币 | 笔数 | 期望 R | | 币 | 笔数 | 期望 R |
|---|---|---|---|---|---|---|
| XLM-USDT | 63 | +0.446R | | ALGO-USDT | 112 | +0.264R |
| ZEC-USDT | 17 | +0.546R | | AAVE-USDT | 109 | +0.279R |
| DASH-USDT | 15 | +0.639R | | ETC-USDT | 108 | +0.210R |
| CHZ-USDT | 97 | +0.288R | | FIL-USDT | 111 | +0.227R |
| | | | | ICP-USDT | 48 | −0.032R |
| | | | | HBAR-USDT | 26 | −0.226R |

8 个样本够大的新币里 6 个正期望。IC/HBAR 是负的——所以不能全盘信新币，
**必须靠相关性簇 + 组合上限管住暴露，而不是靠挑币**。

#### 所以默认改成了什么

`schedule.universe.enabled` 默认 **true**，`filters.max_symbols=30`：
每轮按成交额取前 30 个加密合约，20 个一批轮着深挖。想回到只盯固定列表，
改回 `enabled=false` 即可。

**要诚实说清楚的一点**：这是**用今天的成交额筛选历史数据**，存在幸存者
偏差——2000 天前排在成交额前列的币，很可能已经退场（上一轮 51 个候选里
22 个现在连 K 线都取不到）。所以 28 币的这个数字**偏乐观**，不能当成未来
收益。它能支撑的结论只有一条定性的：**加单比减单更能提升账户收益，且
靠相关性上限能把风险按住。** 定量的部分要靠实盘和影子账户攒。

#### 提胜率：截断"前方没有近距离结构"的单子

前面提过"胜率由目标距离决定"。先把结构量出来（24 币 × 2000 根日线，
2188 笔，逐笔真实规则）：

| 计划盈亏比 | 笔数 | 胜率 | 期望 R | 95% CI | 平均持仓 |
|---|---|---|---|---|---|
| 0.8–1.0 | 430 | **64.0%** | +0.178R | [+0.088, +0.267] | 68h |
| 1.0–1.3 | 557 | 58.0% | +0.214R | [+0.126, +0.299] | 100h |
| 1.3–1.7 | 546 | 50.7% | +0.232R | [+0.129, +0.341] | 120h |
| 1.7–2.5 | 397 | 43.6% | +0.311R | [+0.161, +0.449] | 144h |
| 2.5–3.5 | 166 | 26.5% | +0.051R | [−0.198, +0.310] | 148h |
| >3.5 | 89 | 22.5% | +0.180R | [−0.244, +0.603] | 162h |

胜率随目标距离单调下降——这是盈亏比的本意，不是 bug。**想提胜率就必然
压目标距离，而压目标距离会同时压低每笔盈亏比**，所以单看汇总一定会被骗。

##### 关键是配对检验，不是汇总

加 `analysis.gate.max_target_rr = 2.5`：TP1 取的是**最近的**合格结构位，
它超过 2.5R 说明前方没有近距离的阻力/支撑可依托，这单必须走出很远才回本。
不是我们挑了远目标，是只有远目标可选——所以这条规则改变不了目标距离，
只能选择不做。

逐币配对比较（每币各自跑 cap 开/关）：

| 指标 | 结果 |
|---|---|
| Δ胜率 | **22 个币里 21 个为正，中位数 +2.7pp** |
| Δ期望 | 只有 10/22 为正，中位数 −0.003R、均值 +0.001R |

**胜率稳定提高约 3 个百分点，期望值不变。** 这就是实际结论——没有
"既提胜率又提期望"的好事，那种结论只存在于单次汇总里。第一次跑汇总时
确实看到过"收益 +48%"，换个币池变成 −22%，两次都是噪声；只有配对方向
才可信。

##### 为什么这条不算"质量闸门"

前两次被否掉的修法（分数带、趋势衰减）砍掉的是**期望明确为正**的档
（+0.169R / +0.087R），砍掉就是净损失。而这里砍掉的远目标档，配对检验里
正负各半、中位数 −0.003R——**没有可证明的 edge**。去掉没有 edge 的单子
不亏，换来的是胜率 +3pp、回撤 24.4% → 23.3%，代价是少约 11% 的单量。

##### 顺手补上的诊断：闸门漏斗

加完上限才发现"不知道信号少在哪一步"——只看到交易数掉了，不知道是
评不出方向、还是没有目标位、还是挂了单没成交。所以 `validate` 现在打印
**闸门漏斗**：每个检查点是被哪道闸门挡掉的。

24 币实测：

| 检查点 | 数量 | 占比 |
|---|---|---|
| 合计 | 4147 | 100% |
| 评分低于阈值 | 1128 | 27.2% |
| 盈亏比不足 | 472 | 11.4% |
| 无可用目标位 | 245 | 5.9% |
| 目标位太远 | 244 | 5.9% |
| 挂单未成交 | 118 | 2.8% |
| **实际成交** | 2174 | 52.4% |

这张表当场改了三个判断：

1. **瓶颈不在新加的上限**——"目标位太远"只占 5.9%，而我一直在调它。
   真正的大头是"评分低于阈值"（27%）和"盈亏比不足"（11%）。
2. **拿不到价格/缺 ATR 以前被算进"评分低于阈值"**，漏斗会把数据问题指成
   因子问题。现在它们分开计（`no_price` / `no_atr`）。
3. **118 个检查点挂了单但价格从没进过入场区**（占 2.8%）。这些单子既不算
   胜也不算负，以前完全看不见。

它还让 CLI 能自动给判断，例如"大部分检查点连方向都没评出来（评分低于
阈值）：瓶颈在因子，不在目标位"。

顺带修了一个显示 bug：`state_gate` 里的原因（趋势否决、流动性不足、
评分带、从属模式）在 `signals.py` 里写了四处，但**网页端从来没读过**，
界面上只显示"观望"不给理由。现在会显示具体原因。

#### 顺着漏斗查下去：27% 的"评分低于阈值"是什么

以为是阈值 30 定高了，结果查出两件事，都不是阈值的问题。

##### 1. 回测里 6 个因子其实是死的

交易所的 `history/kline` 只给最近 2000 根，所以各周期的覆盖天数是：

| 周期 | 2000 根覆盖 | 占日线跨度（1999 天） |
|---|---|---|
| 5min | 6.9 天 | 0.3% |
| 15min | 20.8 天 | 1.0% |
| 60min | 83.3 天 | 4.2% |
| 1day | 1999 天 | 100% |

`from` 参数试过，被忽略——**翻不了历史**。于是历史回测里 96.9% 的检查点
只有日线类因子有真实数据，`trend_intraday` / `momentum` / `structure` /
`vwap` / `open_interest` / `elite` 全部恒为 0 分。

按 0 分参与加权平均，等于把"没意见"当成"中性偏空"——方向被稀释。
（实盘不这样，数据是全的，所以实盘评分会比回测更强。）

##### 2. 但"剔除缺数据因子"并没有更好

第一反应当然是让缺数据的因子不参与合成。锁死同一批 24 币快照、只改这
一个开关的 A/B：

| 口径 | 成交 | 胜率 | 单笔期望 | 回撤 | 因子覆盖率 |
|---|---|---|---|---|---|
| 按 0 分参与（默认） | 2022 | 51.6% | +0.1697R | 11.4% | 0.90 |
| 剔除缺数据 | 2065 | 51.6% | +0.1669R | 13.4% | 0.90 |

**差异 0.003R，在噪声内**——两种口径都差不多。所以默认不改，免得让

**这里差点又栽在同一个坑里**：第一轮对比显示"剔除更差"（+0.209R →
+0.167R），看着像强结论。但那次两个口径跑了不同的币池（24 vs 22 个）——
交易所两次返回的合约列表不一样。锁死快照后差异立刻消失。**任何 A/B 不
先锁死输入，结论都不可信。**

##### 3. 真正做的改动：把事实标出来

`plan.factor_coverage` 记录"这次评分有多少权重是真有数据的"，
`plan.dead_factors` 列出哪些因子没数据。`validate` 会算均值，
低于 99% 就在输出里明确警告：

```
闸门漏斗    : 共 582 个检查点（因子覆盖率 90%）
! 回测因子覆盖率 90%：历史 K 线只给最近 2000 根，盘中周期（60min 覆盖
  83 天）够不到 5.5 年的日线跨度，早段检查点缺盘类因子。这些数字验的
  是一个更窄的模型，不代表实盘（实盘因子齐全）。
```

这样每个看报告的人都知道：**这不是"11 个因子一致给出的结论"，
实际只有日线类因子在表态。**

### 滑点不是常数

回测原来把滑点固定成 2bps。这在 BTC 上够用，在薄合约上不对——同样的下单
金额，占当日成交额的比例越高，冲击越大。新增 `iabot/costs.py`，用平方根
冲击模型按订单规模估算：

```python
impact_bps = coeff * sqrt(下单金额 / 当日成交额)   # coeff 默认 30
```

```
450 U 账户 × BTC（5000 万 U 成交额）  ->  冲击 0.13bps，可忽略
450 U 账户 × 小币（100 万 U 成交额）  ->  冲击 0.70bps，值得算
```

`analysis.backtest` 新增 `impact_coeff_bps`（默认 30）和 `maker_fee_bps`
（默认 2）。`impact_coeff_bps = 0` 就退回"固定滑点"的老口径。单笔计划
（`plan.sizing.costs`）现在也把手续费/滑点/冲击摊开显示，不用只在回测里看。

#### 多空不对称：空单是更好的那一半

完整历史上，**空单在上涨市和下跌市都赚钱，多单只在上涨市赚钱**。这是
`trend_veto` 想解决的问题，但"否决"只处理了逆势那部分；更直接的杠杆是
**给两个方向不同的单笔风险**：

```json
"analysis": {
  "risk_mult_long": 1.0,
  "risk_mult_short": 1.0
}
```

`1.0` = 不调整（默认）。实测把多单调到 0.5、空单调到 1.5：

| 配置 | 组合回撤 | 组合收益 |
|---|---|---|
| 1.0 / 1.0 | 18.3% | +2885.8% |
| 0.5 / 1.5 | **16.7%** | +8273.9% |

回撤下降、收益上升，方向是一致的。但**默认仍然是 1.0 / 1.0**——这是调仓
规则，不是过滤器，应该先在影子账户里跑一段时间再改默认值（和 `trend_veto`
同一个标准）。收益数字是复利口径（1000+ 笔 × 2% 滚动），重点看回撤。

`iabot validate --risk-mult-long 0.5 --risk-mult-short 1.5` 可以直接复现。

顺便回答了一个悬着的问题：**trend_veto 该不该默认开**。走动检验的答案是

### 影子账户：改默认值之前先跑一段未来

做法是影子账户：同一批信号，用几套参数各记一份，**只记录不下单**，过一段

不碰信号库的表结构，随时可以删掉重来。

**定时任务会自动记**（`schedule.shadow`，默认开）：每 6 轮把当前关注列表按

### 止损与止盈

- **日内**：止损 = 2.0 × ATR(15m)，止损幅度夹在 0.30%–2.50%；目标位 1.4–14 × ATR(15m)。
- **波段**：止损 = 0.8 × ATR(1day)，止损幅度夹在 1.50%–6.00%；目标位 1.0–9 × ATR(1day)。

入场基准优先挂到附近支撑/阻力上（距离合适时），否则用现价回撤一小段；入场带保证最小宽度，避免挂不进去。
目标位按"先到的先算"排序，取最近 3 档。

#### 保本和移动止损：一个有用，一个有害

出场管理有两种常见做法，都做成了可选（`analysis.exit`，默认都关）：

```json
"exit": { "breakeven_at_r": null, "trail_atr_mult": null }
```

- `breakeven_at_r`：浮盈到这个 R 数就把止损挪到入场价
- `trail_atr_mult`：止损跟着最优价走，距离 = 倍数 × ATR

实测（swing，7 币 × 2000 根日线，692 笔，3 折 = 21 个时间窗）：

| 出场方式 | 期望 R | 95% 区间 | 正收益折 | 胜率 |
|---|---|---|---|---|
| 原始止损 | +0.1278 | [+0.041, +0.221] | 15/21（71%） | 49.3% |
| 保本 1R | +0.1185 | [+0.044, +0.196] | 15/21（71%） | 42.4% |
| 移动止损 1×ATR | +0.1283 | [+0.062, +0.198] | **18/21（86%）** | 35.8% |
| 保本 + 移动 | +0.1335 | [+0.069, +0.202] | 16/21（76%） | 34.9% |

两个结论和直觉相反：

1. **保本单独用是亏的**（+0.1278 → +0.1185）。把止损挪到入场，等于把
   "先回撤再走对"的那批单提前赶下车，而这些单原本是赚的。
2. **移动止损不提高期望，但让 edge 更稳定**：期望几乎不变，可正收益折从
   71% 提到 86%，区间下界从 +0.041 抬到 +0.062。代价是胜率掉到 36%
   （很多单变成小赚出场，不再算"打到止盈"）。

所以默认仍然两个都关——这是**风险偏好**的选择，不是"更优参数"。
想要更平滑的曲线可以只开移动止损；不要只开保本。

### 仓位

```
张数 = floor(账户权益 × 单笔风险% / (止损距离 × 合约面值))
```

若占用保证金超过 `max_margin_pct`，自动缩减张数并在结果里标注。
所以止损被扫掉时，亏损正好被控制在设定的百分比以内。

### 强平价保护

止损只在"能被执行"时才有意义。如果杠杆高到**强平价比止损更靠近入场**，价格会先被强平、
再也走不到止损位——止损形同虚设，但程序原本仍会照常显示"止损亏损 X U"，给出错误的安全感。

所以仓位计算后会校验止损有效性（近似维持保证金率 0.5%，因为 HTX 公开接口不暴露
真实的保证金档位，那需要 API Key）：

```
多仓：强平价 ≈ 入场 × (1 − 1/杠杆 + 0.5%)
空仓：强平价 ≈ 入场 × (1 + 1/杠杆 − 0.5%)
```

- **自动降杠杆**：若强平价更靠近入场，按 `杠杆 < 1/(止损幅度 + 0.5%)` 反推出安全杠杆，
  自动下调并在结果里标注"已因强平风险自动下调"（CLI 与网页都能看到强平价）。
- **模拟盘拦截**：手动录入模拟仓位时，止损会先被强平的话直接拒绝开仓，并提示该用多少倍杠杆。
- 默认 10x 杠杆下不会触发（日内止损 0.3%~2.5%，远在强平之前）。只有把
  `preferred_leverage` 调到几十上百倍才会遇到。

### 两道闸门：评分管方向，盈亏比管位置

评分（±100）只回答"市场现在偏多还是偏空、有多强"，`|评分| ≥ 30` 才给方向。
给了方向之后还要过第二关：**第一目标盈亏比必须 ≥ 1.0**，否则直接降级为观望，
并把原因写进结果里（网页建议卡上那条蓝色说明，CLI 里的 `!!` 那行）。

> ⚠️ **日内模式在扣掉手续费后是负期望，别用它做实盘。** 详见下面「真正的问题」。
> 实盘请用波段模式（+0.327 R/笔，胜率 52.6%）。

所以会出现"评分更高反而观望、评分更低却能做"，同一天的实际例子：

```
SOL  评分 +65.8 → 想做多，但头顶阻力只在 +0.32%，止损却要放到 0.8%
                 → 盈亏比 0.71 → 观望
BTC  评分 +52.8 → 想做多，头顶阻力 +0.44%，止损只要 0.39%
                 → 盈亏比 1.08 → 做多（TP1），后面还有 1.98 / 3.40 两档
```

根因是分母不同：**止损 = 2 × ATR(15m)**。SOL 的 ATR 是 0.409%，止损必须放到 0.8% 开外；
BTC 的 ATR 只有 0.196%，止损 0.39% 就够。同样 0.4% 的空间，对 BTC 是 1.08 倍回报，
对 SOL 连 1 倍都不到 —— 波动大的币，同样的阻力位更"不够远"。

- `|评分| < 阈值` → 观望（`gate` 为空，单纯没方向）
- 评分够但盈亏比 < 1.0 → 观望（`gate.blocked = true`，写明 `would_be` 想做哪边、`rr` 差多少）
- 前方 0.8 倍盈亏比的目标位都找不到 → 观望（`gate.reason = "no_target"`）
- 缺少 ATR 数据、行情接口异常导致关键数据缺失 → 观望

### 闸门判据：回测选出来的，不是拍脑袋

判据本身也是可配的（`analysis.gate.measure`）：`tp1` 只看第一目标、
`weighted` 按 `weights` 给各档加权、`max` 取最好那档。

**默认是 `tp1`，这是回测的结果，不是默认值。** 19 个币 × 1000 根 K 线、
每档 2000~4000 笔、已扣手续费+滑点+资金费：

| 判据 | swing 期望 R | intraday 期望 R |
|---|---|---|
| **tp1（默认）** | **+0.327** | **-0.046** |
| weighted 0.5/0.3/0.2 | +0.310 | -0.047 |
| max | +0.308 | -0.044 |

三者差异在噪声内，换判据并不能提高期望值。`tp1` 反而略优，而且它的语义最直白：
`evaluate_outcome` 是"先到先算"，TP1 正是实际最先命中的那档，等于"这单实际能拿多少 R"。

提高门槛会提高单笔期望、但砍掉信号。**以下数字已计入"必须成交"**

### 胜率为什么只有 50% 上下

**胜率的上限主要由盈亏比几何决定，不是由信号质量决定。** 对随机游走，
入场在中间、止损 -1R、止盈 +TR 时，先到止盈的概率恰好是 `1/(1+RR)`：

| 止盈倍数 | 随机游走基线 | 实测（修复后） | 真实 edge |
|---|---|---|---|
| 0.5 | 45.5% | 52.6% | +7.1pp |
| 0.8 | 42.4% | 49.6% | +7.2pp |
| 1.0 | 39.4% | 46.1% | +6.7pp |
| 1.2 | 36.8% | 42.7% | +5.9pp |
| 1.5 | 32.8% | 37.6% | +4.8pp |

**每个倍数都稳定高出基线 5~7 个百分点**，这是信号真实贡献的地方，且两段时期
都为正。但想靠调参拿到 70~80% 胜率是做不到的——那需要把止盈压到止损的
1/3 以内，期望值会被一起压掉。**胜率和期望值不能同时最大化**，按需选一个。

> ⚠️ 一个曾经失真的指标：`evaluate_outcome` 原先不检查挂单是否成交。
> 多单挂在现价下方，价格直接涨走就永远不会成交，但会被判成"涨到了止盈"——
> 只往里灌水（实测 14% 的信号从未成交，其中 99.7% 被判胜利）。
> 它把胜率从 46.7% 虚抬到 54.0%，期望 R 虚抬了约 2.7 倍。
> 现已要求成交，未成交记为 `no_fill` 并排除在统计外。

### 为什么"看起来全是观望"

实测 20 个主流币：**85% 观望**（日内）/ 75%（波段），拆开是：

| 原因 | 日内 | 波段 |
|---|---|---|
| 无方向（\|评分\| < 30） | 45% | 45% |
| 被盈亏比闸门拦下 | 40% | 30% |
| 正常放行 | 15% | 25% |

**45% 无方向是设计使然**：`score = 100·tanh(加权均值/0.40)`，11 个因子经常互相抵消，
加权均值天然向 0 收缩。而且评分分布是**断层的**——`|评分|` 落在 30~40 区间的样本极少，
所以把阈值从 30 调到 35 或 40，放行数量**完全一样**，调阈值没用。

**剩下 30~40% 被闸门拦下，是评分有方向、但前方空间不够**：
目标位候选门槛是 `min_target_rr`，按 RR 升序取最近的那档作为 TP1，
闸门再要求 TP1 达到 `min_rr`。所以门槛设得比闸门还高时，
闸门会被自己的候选过滤架空——两参数必须满足 `min_target_rr ≤ min_rr`。

### 关于胜率的两个必须知道的数字

1. **胜率上限由盈亏比几何决定**，不是信号质量。RR=1 时无论信号多好，
   先到止盈的概率都在 50% 附近；想要 70%+ 胜率就得把止盈压到止损的 1/3 以内，
   期望值同时被压掉。2. **这个评分的"方向命中率"只有 47~54%，且由市场状态决定**（时序切分实测，
   `sign(评分)` vs 后续实际涨跌；两段之间差异比新旧权重之间差异还大）。
   也就是说**它不是一个方向预测器**。
   它的正期望来自"在支撑附近挂单、止损放在结构之外、止盈放在阻力位"
   这套**盈亏比结构**，以及比随机游走高出 5~7 个百分点的先触止盈概率。

想要真正的方向预测能力，需要换建模思路。调因子权重已验证无效；
样本内唯一稳定的是低波动与成交量两个横截面信号，已给到最高权重，
但单靠它们推不出高置信度的单币方向。

### 真正的问题：日内模式扣掉成本后是亏的

| 模式 | 单笔期望 R | 成本/笔 | 毛利/笔 |
|---|---|---|---|
| swing（止损 1.5~6%） | **+0.156** | +0.027 | +0.183 |
| intraday（止损 0.3~2.5%） | **-0.046** | **+0.182** | +0.136 |

成本 = `费率 × 2 × (名义/风险)`。止损越窄，同样的风险金额要开越大的名义仓位，
手续费和滑点按名义收，于是**成本 R 与止损宽度成反比**。日内止损只有 0.3~2.5%，
往返 14bps 的手续费+滑点就吃掉 0.18 R——毛利 +0.136 全被吃掉。

调宽止损确实能降成本，但毛利跌得更快：

| `stop_atr_mult` | 止损≈ | 成本/笔 | 期望 R |
|---|---|---|---|
| 1.5 | 窄 | +0.214 | -0.020 |
| **2.0（默认）** | | +0.180 | -0.045 |
| 3.0 | 宽 | +0.136 | -0.098 |

**结论：日内模式在当前成本结构下无论怎么调参都是负期望，别用它做实盘。**
波段模式才是有正期望的（+0.327 R/笔，胜率 52.6%）。

### 默认模式为什么是 swing

上一节早就量出日内是负期望，但代码里所有"没指定模式"的入口默认值仍然是
`intraday`——定时任务、CLI、网页 API、参数方案，五个地方各写了一遍字面量。
也就是说产品默认会把用户带进一个已知亏钱的模式。

放开历史长度复测（20 币 × 2000 根 15min，约 20 天，接口上限），确认这个结论
不是小样本假象：

| 模式 | 样本 | 胜率 | 总 R | 单笔期望 R |
|---|---|---|---|---|
| intraday | 10056 笔（9992 已了结） | 50.8% | **-941.57** | **-0.094** |
| swing | 5418 笔 | — | — | **+0.184** |

日内在 18 个有数据的币里 14 个为负。这不是调参能救的：止损越窄手续费占比越高，
宽止损又让毛利跌得更快（见上表）。

所以现在只有一个常量 `iabot.config.DEFAULT_MODE = "swing"`，所有入口都引用它，
测试锁死这个值（改回 intraday 会直接 fail）。

顺带修掉一个绕过口子：参数方案（profiles）会把它的 `mode` 写进 `schedule.mode`
被定时任务真正用上，而保存时对 mode 没做校验——存一个 `reversion` 或打错拼成
`scalp` 的方案，apply 之后定时任务就照着跑。现在 `SCHEDULABLE_MODES` 白名单
在保存、读取、apply、调度器、配置校验五处都生效。

## 完整工作流

把上面的能力串起来就是完整的一条链路。命令行版：

```bat
:: 1) 体检：网络/证书/行情/配置
python -m iabot check

:: 2) 扫一遍关注列表，看谁有信号
python -m iabot scan BTC-USDT,ETH-USDT,SOL-USDT

:: 3) 深度分析单个合约，决定参数方案（网页上拖滑块更直观）
python -m iabot analyze BTC-USDT

:: 4) 历史验证这个参数组合靠不靠谱
python -m iabot backtest BTC-USDT --mode swing --save

:: 5) 多个方案横向对比，挑最优的
::    （网页"参数方案 → 对比全部方案"更直观）

:: 6) 按最优方案开一笔模拟仓，自动带入止损止盈
python -m iabot analyze BTC-USDT --paper

:: 7) 长期盯盘：开着不管，信号变化才提示；Ctrl+C 停
python -m iabot watch --symbols BTC-USDT,ETH-USDT --save

:: 8) 复盘：实测胜率（网页"信号胜率"） + 回测记录对比参数改动
python -m iabot backtests

:: 9) 定期备份（服务运行时会自动备份，这里是手动兜底）
python -m iabot backup
```

网页版把同样的链路做成了面板：控制台 → 参数方案 → 胜率 → 模拟盘 → 利润簿 → 导出报告。

**两条验证路径并存**：
- **历史回测**：用过去的数据评估"这套参数准不准"（`backtest`）
- **实测胜率**：用真实信号跟踪"实际做下来准不准"（`win-stats`，信号会自动回填结局）

两者长期对比，才能判断参数是真的有效，还是只在某段历史行情里好看。

**数据都在 `data/signals.db`**（信号历史 / 模拟持仓 / 回测记录 / 利润簿），服务会每天自动做
一致性快照到 `data/backups/`，最多保留 14 份。`backup` 命令可手动备份/查看。

## 常见问题

**行情拉不到 / 一直转圈**
先跑 `run.bat check`。它会把三个行情域名的探测结果、证书情况、以及一次真实行情请求的耗时都打出来。
国内网络下 `api.hbdm.com` 偶尔会被拦截，程序会自动切到 `api.btcgateway.pro`。

**证书校验失败**
`check` 会提示根证书数量。若为 0，可在 `config.json` 里临时设 `"tls_verify": false`。

**分析一次要多久**
单个合约 3–13 秒（K线、盘口、资金费率、持仓量等并发抓取）。三个行情域名是并发探测的，
而且服务启动时就在后台预热，所以第一个请求不会卡在超时上。同一个合约 20 秒内重复查询会命中缓存，秒回。

**能自动下单吗**
不能，也不会做。本项目只读公开行情接口。

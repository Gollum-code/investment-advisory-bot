# 火币合约行情分析 · 投资建议 (investment-advisory-bot)

拉取火币（HTX）USDT 本位永续合约行情，做多因子打分，输出**可执行**的交易计划：
方向、入场区间、止损、止盈目标、盈亏比，以及按账户权益反推的**张数 / 保证金 / 止损亏损**。

带一个网页控制台：可以选币种、看 K 线与关键价位、也可以开**定时任务循环执行**并把信号落库。

> 只读行情、不下单。所有内容都是分析结果，不构成投资建议。


```bat

python -m iabot analyze BTC-USDT       :: 单个合约，终端直接输出计划
python -m iabot analyze btc --mode swing
python -m iabot analyze BTC-USDT --json --brief
python -m iabot analyze BTC-USDT --save     :: 分析后把这条信号写入历史库
python -m iabot scan BTC-USDT,ETH-USDT,SOL-USDT   :: 批量扫描，按信号强度排序
python -m iabot scan all --top 40            :: 全市场扫描（自动筛出流动性达标的加密币）
python -m iabot scan all --radar            :: 只看全市场雷达表，不做深度分析（1 个请求）
python -m iabot scan all --save             :: 扫描并把有方向的信号写入历史库
python -m iabot backtest BTC-USDT --mode swing   :: 历史回测，统计胜率与期望值
python -m iabot backtest BTC-USDT --save         :: 回测并把参数+结果存档（可事后复现/对比）
python -m iabot backtests --symbol BTC-USDT      :: 查看历史回测记录与参数差异
python -m iabot watch                             :: 终端监控：循环扫描，信号变化时提示（Ctrl+C 退出）
python -m iabot analyze BTC-USDT --paper          :: 分析后直接开一笔模拟仓
python -m iabot backup                            :: 备份信号数据库（信号/持仓/回测/利润簿）
python -m iabot check                  :: 网络 / 证书 / 行情接口 / 配置体检
python -m iabot notify-test           :: 发一条测试通知，验证 notify 渠道配置
```

`analyze` 也接受简写：`python -m iabot btc`。

常用参数：

| 参数 | 说明 |
|---|---|
| `--mode intraday\|swing` | 日内（默认，持仓数小时）或波段（持仓数天~数周） |
| `--equity 450` | 账户权益 USDT，覆盖配置 |
| `--leverage 10` | 杠杆倍数，覆盖配置 |
| `--risk 2` | 单笔最大亏损占账户百分比 |
| `--save` | 把本次分析结果写入信号历史库（SQLite，默认 `data/signals.db`） |
| `--json` / `--brief` | 输出原始 JSON / 不打印因子明细 |

`scan` 常用参数：

| 参数 | 说明 |
|---|---|
| `all` / `全部` | 扫全市场；可与具体合约混写（`BTC-USDT,all`） |
| `--top 40` | 全市场深挖多少个（按排序取前 N） |
| `--min-turnover 100000` | 24h 成交额下限（USDT），过滤僵尸合约 |
| `--all-assets` | 连代币化股票 / 大宗商品一起扫（默认只扫加密币） |
| `--sort turnover\|abs_change\|change` | 候选排序：成交额 / 24h 波动 / 24h 涨跌 |
| `--workers 4` | 并发分析数（调高容易撞火币限流） |
| `--radar` | 只打印全市场雷达表，不做因子打分 |

`backtest` 常用参数：

| 参数 | 说明 |
|---|---|
| `--mode swing` | 回测模式（日内按 15min、波段/超卖反弹按 1day 重放） |
| `--bars 300` | 取多少根主周期 K 线做历史 |
| `--step 3` | 每隔多少根构造一个建仓点（越小越密越慢） |
| `--json` | 输出含 R 权益曲线的原始 JSON |

## 全市场监控

关注列表只有 10 个币，怎么盯住**所有**币？两段式：

1. **广度雷达（1 个请求）**：`batch_merged` 一次拿回交易所全部 400 个 USDT 永续的现价、
   24h 涨跌、成交额；`swap_contract_info` 补上面值与标签，合成一张全市场表。
   网页上就是"全市场雷达"面板，CLI 是 `scan all --radar`。
2. **深度分析**：只对筛出来的候选做完整因子打分。筛选规则在 `universe` 配置块里。

### 为什么不全量深挖

全量 400 个合约每个要 10 个接口，4000 次请求；而且流动性差异极大：

| 合约数 | 24h 成交额 |
|---|---|
| 388 | 全部 USDT 永续（含股票类） |
| ~130 | 纯加密币 |
| 170 | ≥ 10 万 U |
| 23 | ≥ 100 万 U |

成交额中位数只有 **6.5 万 U**，一半合约是几乎没有流动性的僵尸盘——深挖它们既慢又必然被限流。
所以默认口径是「加密币 + 24h 成交额 ≥ 10 万 U + 取前 N 个」，把有限的请求花在能真下的单上。

### 过滤规则（`config.json` 的 `universe`）

| 字段 | 默认 | 说明 |
|---|---|---|
| `enabled` | 关闭 | 是否启用全市场模式（网页/CLI 可临时开，不依赖它） |
| `asset_class` | `crypto` | `crypto`=剔除代币化股票/大宗商品/指数；`all`=全都扫 |
| `min_turnover_usdt` | 100000 | 24h 成交额下限，过滤僵尸合约 |
| `min_price` | 0 | 现价下限，过滤近零价合约 |
| `include_labels` / `exclude_labels` | 空 | 按交易所标签增减。`include_labels` 是"白名单式捞回"：命中标签的合约豁免流动性门槛，排在正常候选之后但**为其预留名额**，不会被 `max_symbols` 截掉 |
| `include` / `exclude` | 空 | 强制纳入 / 排除；`include` 优先级最高（置顶），同样豁免流动性门槛 |
| `max_symbols` | 60 | 深挖上限 |
| `sort` | `turnover` | `turnover` / `abs_change` / `change` |

### 定时任务：分批轮转，不是每轮全扫

勾上「全市场轮询」后，每轮只深挖 `batch_size` 个（默认 20），游标跨轮推进，
全市场转完一圈才回头。这样 130 个币 ÷ 20 = 7 轮轮完，每轮约 50 秒，间隔 300 秒完全跑得动；
也永远只请求 `batch_size × 10` 个接口。设 `batch_size ≥ 全市场数量` 就退化成每轮全扫。

并发数 `workers` 默认 4。实测 8 个合约串行 80.8 秒、并发 4 只要 20.5 秒（快 3.9 倍）；
再往上调收益有限，火币对高频请求会限流（429），程序会指数退避重试。

### 用法

```bat
python -m iabot scan all --radar                    :: 全市场雷达表
python -m iabot scan all --top 40 --save            :: 全市场深挖 + 落库
python -m iabot scan all --min-turnover 1000000     :: 只扫百万 U 以上的大币
python -m iabot scan all --sort abs_change --top 20 :: 扫今天波动最大的 20 个
python -m iabot scan BTC-USDT,all                   :: 指定合约 + 全市场混合
```

网页上：「全市场雷达」面板可调筛选条件并点任意一行跳转分析；「扫描全市场」走并发深挖；
「定时任务」里勾「全市场轮询」设每轮深挖数。

## 网页控制台

- **选币种**：输入框支持任意 `XXX-USDT`，带 80+ 币种中文名/别名下拉；下面还有常用币快捷标签。
- **全市场雷达**：一次请求拉回交易所全部 USDT 永续，按流动性/类别筛选后列出现价、24h 涨跌、成交额与已有信号，点任意一行跳转分析。
- **全市场轮询**：定时任务可切到全市场模式，每轮深挖一批、游标跨轮推进。
- **模式**：日内 / 波段 / 超卖反弹，切换即重算。
- **账户参数**：权益、杠杆、单笔风险，改动立即重算仓位（不写回配置）。
- **行情与关键位**：手绘 K 线（周期可切 1min/5min/15min/60min/1day…），叠加 MA20、成交量、入场区、止损与止盈位。
- **关键价位阶梯**：右侧阻力、左侧支撑，权重条越长越重要（摆动高低点、成交量密集区、斐波那契、均线、整数关口、盘口挂单墙的综合结果）。
- **交易建议**：方向 / 评分 / 置信度 / 入场区间 / 止损 / 止盈列表（含每档预计盈利 U）/ 张数 / 保证金 / 盈亏比 / 风险提示。
- **因子明细**：10 项因子的得分、权重、贡献和文字依据，评分怎么来的看得见。
- **定时任务**：勾选"启用循环执行"，填间隔秒数和合约列表，保存后后台线程开始轮询；可随时"立即执行一轮"。运行日志与历史信号通过 SSE 实时推送到页面。
- **多币种速览**：一键扫描关注列表，按 |评分| 排序，点任意一条跳到该币分析。顶部有市场情绪条（多空占比）。
- **信号胜率**：定时任务跑过的信号会被回填结局（先到目标还是先碰止损），按评分档/模式/置信度/币种/生效方案统计胜率与平均 R。
- **因子权重调参**：网页上拖动 10 个因子的权重滑块与评分阈值，保存到 `config.json`，配合回测与胜率统计找最优组合；可开启"多周期共振"第 11 因子。
- **参数方案**：把"权重+阈值+模式"打包成命名方案，对同一段历史逐个回测对比期望 R，一键应用到实盘扫描与定时任务。胜率面板按方案分组，实测验证哪个方案真的准。
- **模拟盘持仓**：手动录入或从分析结果**一键开模拟仓**（自动填入场/止损/止盈/张数）；自动跟踪浮动盈亏，被止损/止盈打掉时自动平仓记录；现价逼近止损时推送预警。带**利润簿**：已平仓盈亏按周/月/总汇总、胜率、权益曲线（扣手续费）。
- **通知**：配置 Telegram / Bark / 通用 Webhook 后，方向翻转与强信号实时推送（`config.json` 的 `notify` 块）。
- **导出报告**："导出报告"按钮打开一页自包含 HTML（内联 SVG K 线 + 建议 + 胜率 + 因子），浏览器打印即可存成 PDF，便于存档分享。

网页上改定时任务、因子权重和参数方案会写回 `config.json`，重启后依然生效。

## 回测与成本

`python -m iabot backtest BTC-USDT --mode swing` 在历史 K 线上滑动回放：每隔若干根
构造一个"当时的快照"（只用该点及之前的数据，无未来函数），走真实的打分与两道闸门，
再用后续 K 线判定结果。

每笔交易都会扣三项成本，全部折算成 R（成本占单笔风险的比例）：

| 成本 | 怎么算 |
|---|---|
| 手续费 | `taker_fee_bps × 2 × (名义/风险)`，开平各一次 |
| 滑点 | `slippage_bps × 2 × (名义/风险)`，开平各一次 |
| 资金费 | 按**持仓时长**累计：费率 × (持仓小时 / 8) × (名义/风险)；费率为正时多头付、空头收 |

资金费用的是**每个建仓点当时生效的费率**（取自 HTX `swap_historical_funding_rate`
历史序列），不是拿"当前费率"套全部历史——后者在费率剧烈波动的行情里会让回测严重失真。

参数在 `config.json` 的 `analysis.backtest` 里（费率、滑点 bps、是否计资金费）。
输出里的"期望 R"已扣成本，正数才代表长期按规则做有优势；同时会按你的账户权益和单笔
风险折算出金额（`--equity` / `--risk` 可覆盖）。

### 回测实验记录

`backtest --save` 会把这次回测存成一条实验记录，网页和 `backtests` 命令都能看。
关键在于**存的是完整参数快照**（权重、阈值、共振开关、成本参数、步长、账户口径），
而不只是一个模式名——这样几个月后能复现那次结果，也能并排对比：

```
$ python -m iabot backtests
  #3  BTC-USDT  intraday   胜率 60.0%  期望 +0.412 R  24 笔  期末 520 U
  #2  BTC-USDT  swing      胜率 55.0%  期望 +0.180 R  11 笔  期末 466 U

  与上一条相比改了：
    - 模式: swing → intraday
    - 权重 momentum: 0.15 → 0.4
```

网页上"参数方案"卡片里勾选"回测时存档"，做方案对比时会一次性把每个方案的结果都记下来。

## 它是怎么算的

### 因子与权重

| 因子 | 权重 | 看什么 |
|---|---|---|
| 波动率 | 0.30 | 当前 ATR% 在自身近 250 天中的百分位（越低越多） |
| 成交量 | 0.18 | 成交量 z-score 相对前 20 日均值（放量偏空） |
| 日线趋势 | 0.10 | 价格 vs SMA20/50/200、EMA12/26 |
| 资金费率 | 0.08 | 费率相对自身 30 日均值的偏离（过热反向） |
| 大户持仓 | 0.06 | 大户多空净比相对自身基线的偏离（σ） |
| 持仓量 | 0.06 | OI 变化与价格方向是否共振 |
| 动量 | 0.06 | RSI、近期涨跌幅（弱反向） |
| 摆动结构 | 0.05 | 分形高低点是否抬高/降低 + ADX 判趋势市/震荡市 |
| 1小时趋势 | 0.04 | 价格 vs SMA20/50、MACD 柱状 |
| 盘口深度 | 0.04 | 买卖挂单墙的偏向 |
| VWAP | 0.03 | 现价相对当日成交量加权均价 |

> 权重来自样本外检验，不是手感。检验方法和结论见下面
> 「哪些信号真的有预测力」。趋势类因子给了低权重，是因为它们的
> IC 符号在训练/测试两段里会翻转，**无法用于定方向**，只能当参与项。

> 旧版的一个硬缺陷：因子函数里的权重和 `FACTOR_DEFAULTS` 各自写死一份，
> 实际生效的是函数里那份，改配置不动行为。现已统一由 `_w(name)`
> 单点读取，并在 `compute_factors` 末尾做一次归一化。

加权平均天然向 0 收缩（因子经常互相抵消），所以评分用
`score = 100 · tanh(加权均值 / 0.40)` 压缩：中间区域放大，极端区域饱和。
`|score| ≥ 30` 才给方向，否则观望（超卖反弹模式除外——它走独立判据，不评分）。

### 哪些信号真的有预测力

把每个因子单独拿出来做 IC 检验（19~23 币 × 1000 根日线，**按时间切成 60/40**，
前半定方向后半验证）。结果是：

| 因子 | 训练段 IC | 测试段 IC | 结论 |
|---|---|---|---|
| 波动率 `atrp` / `hl` | + | + | **稳定可用** |
| 成交量 `volz` | + | + | **稳定可用** |
| MACD 反向 | + | + | 弱，可用 |
| 日线/1小时趋势 | − | + 或 0 | **符号翻转，不可用** |
| RSI | − | + | **符号翻转，不可用** |
| 摆动结构 | − | + | **符号翻转，不可用** |
| VWAP | − | 0 | **符号翻转，不可用** |

趋势类因子训练段 IC 是负的、测试段转正或归零——**方向在样本外根本不可靠**，
把它们压到低权重当"参与项"而不是"方向源"。

真正稳定的是**低波动**：把币按当前 ATR% 分三档，**低波动档在两个时间段都多赚**

| ATR% 分档 | 前半段 6 日收益 | 后半段 6 日收益 |
|---|---|---|
| 低 | **+0.75%** | **+0.72%** |
| 中 | +0.31% | +0.34% |
| 高 | +0.02% | +0.00% |

稳定子集（波动率 + 成交量 + MACD 反向）合成的复合信号：
训练 IC +0.035 / 测试 IC **+0.026**，命中率 **52.1% / 51.5% / 51.8%**，
两段都过半。所以波动率和成交量拿到了最高的两个权重。

`_f_volatility` 和 `_f_volume` 都是**相对自身历史**的百分位/z-score，
不是绝对值——同一套阈值在 BTC 和山寨币上语义完全不同，
用绝对阈值必然一头饱和（旧版 `_f_elite` / `_f_funding` 就是这个毛病：
用绝对净比和绝对费率，结果 39/40 个币全在 ≤0 的同一侧，因子退化成常数偏空）。

### 这个评分的方向预测能力依然很弱

**不是反向，是接近无效。** 完整 `build_plan` 的命中率（时序切分）：

| 模型 | 训练段 | 测试段 |
|---|---|---|
| 旧权重 | 46.9% | 53.6% |
| 新权重 | 48.4% | **53.6%** |

测试段完全一样。**命中率由市场状态决定，不由权重决定**——换权重救不了它。
新模型的改善在于：横截面一致性从"18 个看空 1 个看多"的常数偏空，
变成跟市场同步（实测一次扫描 15 个空 / 0 个多，15 个方向全部正确）。

所以别把"方向"当预测用。它更像一个"该往哪边挂单"的过滤器，
正期望来自盈亏比结构，不来自方向判断。

### 跌段做多为什么修不掉，以及另开的一条通道

多因子模型在跌段里做多是亏的（20 币 × 2060 建仓点、5 日持有、时序切分 60/40）：

| 区段 | 基准上涨率 | long 命中 | short 命中 |
|---|---|---|---|
| train（跌段） | 43.1% | 41.3% | **57.0%** |
| test（涨段） | 52.7% | **52.7%** | 50.4% |

试过五种修法，全部失败：

| 候选闸门 | 结果 |
|---|---|
| price vs SMA 锚拦 long | 上方 42.6% / 下方 40.9%，无差异 |
| 状态与趋势同向才开仓 | 涨段 short 53.9% → 44%，砍掉唯一正 edge |
| 纯趋势跟随 | 同上 |
| long 需趋势确认（不对称） | 涨段 long 55.0% → 50.5%，整体 47.6% → 46.9% |
| 按 plan.rr 分桶 | 跌段 long 亏损均匀铺开，不在任何 rr 档集中 |

原因不是"没调好"，是**edge 本身不对称**：做空在两个区段都赚，做多只在涨段赚。
任何"拦一边"的闸门都是用一侧 edge 换另一侧，数据里不存在"跌段接飞刀还赚"的 alpha。

所以没有去加第七个闸门，而是承认缺一个策略，另开一条通道——**超卖反弹**
（`--mode reversion`）：跌势里跌透了，博 1~2 天回抽，目标位就是回到 SMA20。

触发三条缺一不可：`RSI(2) < 10` 且 `close < SMA20×1.03` 且 `close < SMA200`。
只做多（反弹没有空头对应物，跌势追空归波段）。

留出法验证（20 币日线，每币前 60% 定触发、后 40% 验证）：

| 触发 | 训练段 | 测试段 |
|---|---|---|
| RSI(2)<10 & <SMA20 & <SMA200，持 2 日 | 65.6% / +6.59% | **65.6% / +6.61%**（n=32） |
| 对照：跌势任意点做多，持 2 日 | 52.9% / +3.97% | 同 |

训练段和测试段一致，不是过拟合。走完整回测（含成交/止损/止盈判定与手续费）：
**77 笔交易、已了结胜率 50.7%、总 R +26.02、单笔期望 +0.366R**——
高于波段的 +0.327R，而且它成交的正是波段模型做不了 long 的区间。

### 止损与止盈

- **日内**：止损 = 2.0 × ATR(15m)，止损幅度夹在 0.30%–2.50%；目标位 1.4–14 × ATR(15m)。
- **波段**：止损 = 0.8 × ATR(1day)，止损幅度夹在 1.50%–6.00%；目标位 1.0–9 × ATR(1day)。

入场基准优先挂到附近支撑/阻力上（距离合适时），否则用现价回撤一小段；入场带保证最小宽度，避免挂不进去。
目标位按"先到的先算"排序，取最近 3 档。

### 仓位

```
张数 = floor(账户权益 × 单笔风险% / (止损距离 × 合约面值))
```

若占用保证金超过 `max_margin_pct`，自动缩减张数并在结果里标注。
所以止损被扫掉时，亏损正好被控制在设定的百分比以内。

### 强平价保护

止损只在"能被执行"时才有意义。如果杠杆高到**强平价比止损更靠近入场**，价格会先被强平、
再也走不到止损位——止损形同虚设，但程序原本仍会照常显示"止损亏损 X U"，给出错误的安全感。

所以仓位计算后会校验止损有效性（近似维持保证金率 0.5%，因为 HTX 公开接口不暴露
真实的保证金档位，那需要 API Key）：

```
多仓：强平价 ≈ 入场 × (1 − 1/杠杆 + 0.5%)
空仓：强平价 ≈ 入场 × (1 + 1/杠杆 − 0.5%)
```

- **自动降杠杆**：若强平价更靠近入场，按 `杠杆 < 1/(止损幅度 + 0.5%)` 反推出安全杠杆，
  自动下调并在结果里标注"已因强平风险自动下调"（CLI 与网页都能看到强平价）。
- **模拟盘拦截**：手动录入模拟仓位时，止损会先被强平的话直接拒绝开仓，并提示该用多少倍杠杆。
- 默认 10x 杠杆下不会触发（日内止损 0.3%~2.5%，远在强平之前）。只有把
  `preferred_leverage` 调到几十上百倍才会遇到。

### 两道闸门：评分管方向，盈亏比管位置

评分（±100）只回答"市场现在偏多还是偏空、有多强"，`|评分| ≥ 30` 才给方向。
给了方向之后还要过第二关：**第一目标盈亏比必须 ≥ 1.0**，否则直接降级为观望，
并把原因写进结果里（网页建议卡上那条蓝色说明，CLI 里的 `!!` 那行）。

> ⚠️ **日内模式在扣掉手续费后是负期望，别用它做实盘。** 详见下面「真正的问题」。
> 实盘请用波段模式（+0.327 R/笔，胜率 52.6%）。

所以会出现"评分更高反而观望、评分更低却能做"，同一天的实际例子：

```
SOL  评分 +65.8 → 想做多，但头顶阻力只在 +0.32%，止损却要放到 0.8%
                 → 盈亏比 0.71 → 观望
BTC  评分 +52.8 → 想做多，头顶阻力 +0.44%，止损只要 0.39%
                 → 盈亏比 1.08 → 做多（TP1），后面还有 1.98 / 3.40 两档
```

根因是分母不同：**止损 = 2 × ATR(15m)**。SOL 的 ATR 是 0.409%，止损必须放到 0.8% 开外；
BTC 的 ATR 只有 0.196%，止损 0.39% 就够。同样 0.4% 的空间，对 BTC 是 1.08 倍回报，
对 SOL 连 1 倍都不到 —— 波动大的币，同样的阻力位更"不够远"。

- `|评分| < 阈值` → 观望（`gate` 为空，单纯没方向）
- 评分够但盈亏比 < 1.0 → 观望（`gate.blocked = true`，写明 `would_be` 想做哪边、`rr` 差多少）
- 前方 0.8 倍盈亏比的目标位都找不到 → 观望（`gate.reason = "no_target"`）
- 缺少 ATR 数据、行情接口异常导致关键数据缺失 → 观望

### 闸门判据：回测选出来的，不是拍脑袋

判据本身也是可配的（`analysis.gate.measure`）：`tp1` 只看第一目标、
`weighted` 按 `weights` 给各档加权、`max` 取最好那档。

**默认是 `tp1`，这是回测的结果，不是默认值。** 19 个币 × 1000 根 K 线、
每档 2000~4000 笔、已扣手续费+滑点+资金费：

| 判据 | swing 期望 R | intraday 期望 R |
|---|---|---|
| **tp1（默认）** | **+0.327** | **-0.046** |
| weighted 0.5/0.3/0.2 | +0.310 | -0.047 |
| max | +0.308 | -0.044 |

三者差异在噪声内，换判据并不能提高期望值。`tp1` 反而略优，而且它的语义最直白：
`evaluate_outcome` 是"先到先算"，TP1 正是实际最先命中的那档，等于"这单实际能拿多少 R"。

提高门槛会提高单笔期望、但砍掉信号。**以下数字已计入"必须成交"**
（价格没进过挂单区就不算一笔交易）：

| `min_rr` | 成交笔数 | 胜率 | 期望 R | 总 R |
|---|---|---|---|---|
| 0.5 | 4490 | 52.6% | +0.145 | +649 |
| **0.8（默认）** | 3709 | **49.6%** | **+0.156** | **+581** |
| 1.0 | 2986 | 46.1% | +0.151 | +450 |
| 1.2 | 2321 | 42.7% | +0.144 | +335 |
| 1.5 | 1503 | 37.6% | +0.126 | +190 |

选 0.8 是因为它在**两段时期里都是"胜率更高、期望值不降"的占优选择**
（时序切分验证，非单一样本）：

| `min_rr` | 前半段（bar 60-458） | 后半段（bar 520-995） |
|---|---|---|
| 0.5 | 51.1% / +0.137R | 56.5% / +0.174R |
| **0.8** | **47.9% / +0.139R** | **53.0% / +0.198R** |
| 1.0 | 44.9% / +0.131R | 48.5% / +0.187R |
| 1.2 | 41.2% / +0.111R | 45.4% / +0.195R |

### 胜率为什么只有 50% 上下

**胜率的上限主要由盈亏比几何决定，不是由信号质量决定。** 对随机游走，
入场在中间、止损 -1R、止盈 +TR 时，先到止盈的概率恰好是 `1/(1+RR)`：

| 止盈倍数 | 随机游走基线 | 实测（修复后） | 真实 edge |
|---|---|---|---|
| 0.5 | 45.5% | 52.6% | +7.1pp |
| 0.8 | 42.4% | 49.6% | +7.2pp |
| 1.0 | 39.4% | 46.1% | +6.7pp |
| 1.2 | 36.8% | 42.7% | +5.9pp |
| 1.5 | 32.8% | 37.6% | +4.8pp |

**每个倍数都稳定高出基线 5~7 个百分点**，这是信号真实贡献的地方，且两段时期
都为正。但想靠调参拿到 70~80% 胜率是做不到的——那需要把止盈压到止损的
1/3 以内，期望值会被一起压掉。**胜率和期望值不能同时最大化**，按需选一个。

> ⚠️ 一个曾经失真的指标：`evaluate_outcome` 原先不检查挂单是否成交。
> 多单挂在现价下方，价格直接涨走就永远不会成交，但会被判成"涨到了止盈"——
> 只往里灌水（实测 14% 的信号从未成交，其中 99.7% 被判胜利）。
> 它把胜率从 46.7% 虚抬到 54.0%，期望 R 虚抬了约 2.7 倍。
> 现已要求成交，未成交记为 `no_fill` 并排除在统计外。

### 为什么"看起来全是观望"

实测 20 个主流币：**85% 观望**（日内）/ 75%（波段），拆开是：

| 原因 | 日内 | 波段 |
|---|---|---|
| 无方向（\|评分\| < 30） | 45% | 45% |
| 被盈亏比闸门拦下 | 40% | 30% |
| 正常放行 | 15% | 25% |

**45% 无方向是设计使然**：`score = 100·tanh(加权均值/0.40)`，11 个因子经常互相抵消，
加权均值天然向 0 收缩。而且评分分布是**断层的**——`|评分|` 落在 30~40 区间的样本极少，
所以把阈值从 30 调到 35 或 40，放行数量**完全一样**，调阈值没用。

**剩下 30~40% 被闸门拦下，是评分有方向、但前方空间不够**：
目标位候选门槛是 `min_target_rr`，按 RR 升序取最近的那档作为 TP1，
闸门再要求 TP1 达到 `min_rr`。所以门槛设得比闸门还高时，
闸门会被自己的候选过滤架空——两参数必须满足 `min_target_rr ≤ min_rr`。

### 关于胜率的两个必须知道的数字

1. **胜率上限由盈亏比几何决定**，不是信号质量。RR=1 时无论信号多好，
   先到止盈的概率都在 50% 附近；想要 70%+ 胜率就得把止盈压到止损的 1/3 以内，
   期望值同时被压掉。
2. **这个评分的"方向命中率"只有 47~54%，且由市场状态决定**（时序切分实测，
   `sign(评分)` vs 后续实际涨跌；两段之间差异比新旧权重之间差异还大）。
   也就是说**它不是一个方向预测器**。
   它的正期望来自"在支撑附近挂单、止损放在结构之外、止盈放在阻力位"
   这套**盈亏比结构**，以及比随机游走高出 5~7 个百分点的先触止盈概率。

想要真正的方向预测能力，需要换建模思路。调因子权重已验证无效；
样本内唯一稳定的是低波动与成交量两个横截面信号，已给到最高权重，
但单靠它们推不出高置信度的单币方向。

### 真正的问题：日内模式扣掉成本后是亏的

| 模式 | 单笔期望 R | 成本/笔 | 毛利/笔 |
|---|---|---|---|
| swing（止损 1.5~6%） | **+0.156** | +0.027 | +0.183 |
| intraday（止损 0.3~2.5%） | **-0.046** | **+0.182** | +0.136 |

成本 = `费率 × 2 × (名义/风险)`。止损越窄，同样的风险金额要开越大的名义仓位，
手续费和滑点按名义收，于是**成本 R 与止损宽度成反比**。日内止损只有 0.3~2.5%，
往返 14bps 的手续费+滑点就吃掉 0.18 R——毛利 +0.136 全被吃掉。

调宽止损确实能降成本，但毛利跌得更快：

| `stop_atr_mult` | 止损≈ | 成本/笔 | 期望 R |
|---|---|---|---|
| 1.5 | 窄 | +0.214 | -0.020 |
| **2.0（默认）** | | +0.180 | -0.045 |
| 3.0 | 宽 | +0.136 | -0.098 |

**结论：日内模式在当前成本结构下无论怎么调参都是负期望，别用它做实盘。**
波段模式才是有正期望的（+0.327 R/笔，胜率 52.6%）。

## 完整工作流

把上面的能力串起来就是完整的一条链路。命令行版：

```bat
:: 1) 体检：网络/证书/行情/配置
python -m iabot check

:: 2) 扫一遍关注列表，看谁有信号
python -m iabot scan BTC-USDT,ETH-USDT,SOL-USDT

:: 3) 深度分析单个合约，决定参数方案（网页上拖滑块更直观）
python -m iabot analyze BTC-USDT

:: 4) 历史验证这个参数组合靠不靠谱
python -m iabot backtest BTC-USDT --mode swing --save

:: 5) 多个方案横向对比，挑最优的
::    （网页"参数方案 → 对比全部方案"更直观）

:: 6) 按最优方案开一笔模拟仓，自动带入止损止盈
python -m iabot analyze BTC-USDT --paper

:: 7) 长期盯盘：开着不管，信号变化才提示；Ctrl+C 停
python -m iabot watch --symbols BTC-USDT,ETH-USDT --save

:: 8) 复盘：实测胜率（网页"信号胜率"） + 回测记录对比参数改动
python -m iabot backtests

:: 9) 定期备份（服务运行时会自动备份，这里是手动兜底）
python -m iabot backup
```

网页版把同样的链路做成了面板：控制台 → 参数方案 → 胜率 → 模拟盘 → 利润簿 → 导出报告。

**两条验证路径并存**：
- **历史回测**：用过去的数据评估"这套参数准不准"（`backtest`）
- **实测胜率**：用真实信号跟踪"实际做下来准不准"（`win-stats`，信号会自动回填结局）

两者长期对比，才能判断参数是真的有效，还是只在某段历史行情里好看。

**数据都在 `data/signals.db`**（信号历史 / 模拟持仓 / 回测记录 / 利润簿），服务会每天自动做
一致性快照到 `data/backups/`，最多保留 14 份。`backup` 命令可手动备份/查看。

## 常见问题

**行情拉不到 / 一直转圈**
先跑 `run.bat check`。它会把三个行情域名的探测结果、证书情况、以及一次真实行情请求的耗时都打出来。
国内网络下 `api.hbdm.com` 偶尔会被拦截，程序会自动切到 `api.btcgateway.pro`。

**证书校验失败**
`check` 会提示根证书数量。若为 0，可在 `config.json` 里临时设 `"tls_verify": false`。

**分析一次要多久**
单个合约 3–13 秒（K线、盘口、资金费率、持仓量等并发抓取）。三个行情域名是并发探测的，
而且服务启动时就在后台预热，所以第一个请求不会卡在超时上。同一个合约 20 秒内重复查询会命中缓存，秒回。

**能自动下单吗**
不能，也不会做。本项目只读公开行情接口。
